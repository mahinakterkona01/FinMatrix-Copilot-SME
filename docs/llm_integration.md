**Theme:** AI as a Financial Participant

## 1. Overview

FinMatrix Copilot is a Streamlit-based financial decision-support prototype designed to help small and medium-sized businesses understand financial data and explore cash-flow-related questions.

The language-model integration is intended to make financial information easier to understand through natural-language questions and explanations. It complements the application's financial processing and analysis components rather than replacing them.

The exact capabilities available to users depend on the current implementation, provider configuration, and availability of the required services.

## 2. Role of the Language Model

A language model can help interpret user questions, explain financial concepts, and produce readable summaries from relevant information.

For a financial application, however, a generated response should not automatically be treated as a verified calculation or a reliable prediction.

FinMatrix follows the design principle of separating numerical financial operations from natural-language explanations wherever the implementation supports that separation.

The intended responsibilities are:

- **Financial processing:** Validate and normalize input data.
- **Financial tools:** Perform supported calculations using application logic.
- **Forecasting:** Estimate future values using the implemented forecasting method.
- **Retrieval:** Locate relevant information from available documents, where configured.
- **Language model:** Help interpret questions and explain available results.
- **User review:** Allow users to inspect the results and make the final decision.

This describes the intended separation of responsibilities. Each connection should be verified against the current source code before being presented as a fully implemented workflow.

## 3. Integration Architecture

The intended high-level workflow is:

1. The user enters a question or provides supported financial data.
2. The application validates and processes the available input.
3. Relevant financial calculations or retrieval operations are performed where supported.
4. The language model receives the information required for the requested task, if the feature is enabled.
5. The application presents the resulting explanation or output.
6. The user reviews the result before making a financial decision.

The language model should not be assumed to have direct access to every application component or to execute every financial operation. Its actual permissions depend on the implemented integration.

## 4. Configuration

External language-model services may require an API credential and provider-specific configuration.

Credentials should be supplied through environment variables or an appropriate secrets-management mechanism. They should not be hardcoded into source files or committed to GitHub.

For example, PowerShell can set an environment variable for the current session:

```powershell
$env:OPENAI_API_KEY = "YOUR_API_KEY"
```

The variable name is illustrative. Confirm the exact name and configuration expected by `src/llm_client.py` before using it.

If the integration depends on an external provider, successful configuration also depends on account access, available credits, usage limits, network connectivity, and the provider's current service status.

A missing credential or unavailable provider should be treated as an integration failure, not as evidence that a live model response was generated.

## 5. Financial Calculations and AI Responses

Financial calculations can be sensitive to rounding, missing values, inconsistent date formats, and incorrect assumptions.

Where deterministic application logic is available, numerical results should be calculated by the relevant financial tools rather than estimated solely through natural-language generation.

The application should preserve the distinction between:

- Values calculated from supplied financial data.
- Forecasts generated by a forecasting method.
- Information retrieved from documents.
- Explanations generated by a language model.
- Assumptions or recommendations that require user review.

This distinction helps users understand the source and reliability of each result.

## 6. Retrieval-Augmented Generation

Retrieval-augmented generation (RAG) combines information retrieval with language-model generation. It can help a system answer questions using relevant passages from a document collection.

If RAG is enabled in FinMatrix Copilot, its intended workflow is:

1. Receive a user question.
2. Retrieve potentially relevant information from the configured document collection.
3. Provide the relevant context to the language model.
4. Generate an answer informed by that context.
5. Present source information where the implementation supports it.

Retrieval does not guarantee that the returned documents are complete, accurate, or relevant. A model may also generate claims that are not supported by the retrieved context.

For this reason, retrieval-based answers should be evaluated separately from numerical financial calculations. Any claim that source citations, document indexing, or a particular retrieval method is implemented should be confirmed against the current code.

## 7. Error Handling and Availability

External model calls may fail because of invalid credentials, exhausted credits, rate limits, network errors, or provider outages.

A reliable integration should:

- Detect and communicate provider failures clearly.
- Avoid exposing credentials in error messages or logs.
- Avoid presenting a failed request as a successful AI response.
- Preserve access to independent financial functions where the application supports them.
- Avoid unlimited retries that may increase cost or delay the user.

The exact fallback behavior should be verified through testing rather than assumed from the architecture.

## 8. Privacy and Data Handling

Financial records may contain sensitive business information. Before sending any data to an external model provider, the application should limit the information to what is necessary for the requested operation.

The following areas require attention:

- Which financial fields are sent to the provider.
- Whether uploaded documents or retrieved passages are included in prompts.
- Whether prompts or responses are retained in logs.
- Whether sensitive values can appear in generated reports.
- Whether the provider's applicable data-handling terms meet the project's requirements.

API credentials must remain private. The use of an API key alone does not establish user authentication or protect uploaded financial data.

## 9. Evaluation

LLM behavior should be evaluated separately from the application's deterministic financial logic.

Useful evaluation areas include:

- Relevance to the user's question.
- Factual consistency with the available financial data.
- Correct interpretation of retrieved information.
- Clear communication of assumptions and uncertainty.
- Handling of missing or conflicting context.
- Resistance to selected prompt-injection scenarios.
- Correct behavior when the provider is unavailable.

Evaluation results should be reported only when supported by actual tests or documented experiments. Passing a small set of examples does not guarantee that all future responses will be accurate.

## 10. Current Limitations

Language-model integration introduces uncertainty that cannot be eliminated through prompting alone.

A model may misunderstand a question, omit important context, generate unsupported statements, or produce an answer that sounds more certain than the evidence justifies.

Retrieval quality depends on the available documents and retrieval implementation. External-service availability may also depend on account limits and configuration.

FinMatrix Copilot should therefore be treated as a decision-support prototype. Important financial outputs require appropriate verification and human judgment.

## 11. Future Improvements

Potential improvements include:

1. More systematic evaluation of financial question-answering tasks.
2. Better identification of the data and sources supporting each response.
3. Stronger tests for untrusted documents and prompt injection.
4. Clearer handling of missing context and uncertain answers.
5. Improved monitoring of provider failures and usage limits.
6. More comprehensive privacy checks for prompts, logs, and generated reports.

These are future improvement areas unless their implementation has been independently verified.

## 12. Conclusion

The purpose of LLM integration in FinMatrix Copilot is to make financial information more accessible through natural-language interaction while retaining appropriate boundaries around calculations, data access, and decision-making.

Team FinMatrixDUO aims to develop this integration responsibly by evaluating generated responses, documenting limitations, and ensuring that AI-assisted explanations do not replace verification of important financial results.

## Local Ollama setup and safety notes

The supported local configuration uses these `.env` entries:

```dotenv
FINMATRIX_LLM_PROVIDER=ollama
FINMATRIX_ENABLE_OLLAMA=true
OLLAMA_BASE_URL=http://127.0.0.1:11434
OLLAMA_MODEL=llama3.2:3b
```

Install and start Ollama, then verify the model with `ollama list`. The app's
LLM client sends requests to the configured local Ollama endpoint. When
configured for local inference, prompts do not need to be sent to an external
LLM API. This is not a blanket privacy guarantee: logs, other integrations,
network settings, or user actions may still expose data.

The model provides optional natural-language assistance, not authoritative
financial advice. Deterministic calculations and security refusals must remain
unchanged by model rewrites. Policy questions must retain the existing
retrieval/evidence route. If generation fails or a rewrite is rejected, the
application should preserve the original answer.

Before submission, verify a normal question, a deterministic financial query,
a policy question, and a security-guardrail query in the Streamlit UI. Keep
`.env`, customer data, credentials, and local backups out of the submission.
